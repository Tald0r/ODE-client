# Sprite asset audit (2026-09-23)

The offline Windows ASan audit accepted **193 distinct installed files,
345,531 declared records and 531,564 decoder calls**. Files were matched to
their production callers and formats, then read through the production sprite
libraries. This is parser/index evidence, not a game-rendering run. File
extensions alone are insufficient: `.spk` and `.aspk` name several formats.

The [inventory](references/sprite-asset-inventory-2026-09-23.tsv) records relative paths,
formats, read paths and declared counts. Its counts are from each pack's
little-endian 16-bit header, with case aliases deduplicated for the Windows
installation. The 151 UI files map to 209 constant-path call sites. An earlier
152-path total counted `ArrowTile.spk` twice; its 76 records and 152 decoder
calls are counted once here. Earlier 75-file UI results are a subset.

Indexed reads validate the complete index and seek every declared target,
including appended records that a sequential scan missed. Complete eager packs
use the actual pack loader. The six title/disconnect records use the changed
`CFileIndexTable`; the 4,758 guild-mark records use the shared running-index
helper and both pixel decoders. The audit does not simulate the guild cache.

The temporary harness links the repository's ASan `SpriteLib`, `basic` and
dependent libraries. It records path, format, record ID, byte offset and
rejections; success requires no rejected records, truncation or bad indexes.
Manifests and logs are retained locally under `build/sprite-audit/`. Installed
art and the machine-specific harness are not repository test fixtures.

## Caller classification and limits

- `FrdWinSlayer.spk`, `FrdWinVampire.spk` and `FrdWinOusters.spk`, referenced at
  six UI sites, are absent from this installation. They have no asset-validation
  claim. The checked reader rejects missing files without publishing a pack.
- Dynamic profile packs are generated locally by `ProfileManager::InitProfiles`
  through `SetPixelNoColorkey` and sprite/index saves. The active writer creates
  30x38 and 55x70 placeholders. No installed profile samples were available or
  generated by this audit; generated-sprite behavior has library tests.
- No active construction was found for `C_ANI_OBJECT`'s filename wrapper or the
  four `MLoadingSPKWorkNode` variants. The work-node references outside their
  implementations are type-size diagnostics. Commented constructions do not
  establish live asset formats.
- No active callers of `CSpritePackList`, `CSpritePalPackList` or
  `CAlphaSpritePackList` were found outside SpriteLib in Client, VS_UI or tools.
  `CAlphaSpritePack` is also a latent API: current game alpha resources use
  `CAlphaSpritePalPack`. Library fixtures own those latent decoder contracts;
  no installed asset coverage is inferred from their names.
- Unreferenced trailing bytes are outside the claim. In particular,
  `ItemDrop.ispk` has 4,296 bytes beyond its declared entries. Six files in the
  initial UI subset also had sequential trailing bytes; indexed visits cover
  their referenced records, not every byte in the files.
- Both pixel formats were exercised offline. The running SDL game selects 565;
  555 coverage is latent compatibility evidence. Short decoded rows remain
  valid under the format's upper-bound rule.

## Regression owners and error propagation

Malformed-input and ownership contracts remain in `test_ctypepack.cpp`,
`test_ctypepack_indexed.cpp`, `test_file_index_table.cpp`, the pixel/index/alpha
sprite tests, `test_alpha_sprite_pack.cpp`, `test_cfilter.cpp`, palette
tests and surface/backend tests. These fixtures supply repeatable checks
without depending on installed art.

Pack readers report file/record failures. Startup and display restoration check
their pack opens; ending events clean up failed loads; title/disconnect and
guild-mark callers publish only accepted results. Addon and creature preloads
check partial results before setting loaded flags. Zone loading checks tile
preload and image-pack reopening. Lazy records are decoded at first use, so a
successful index open does not claim that every future record has decoded.
Game-global wiring is covered by source review and full builds; it is not a
runtime reproduction. Live-server verification remains optional.
